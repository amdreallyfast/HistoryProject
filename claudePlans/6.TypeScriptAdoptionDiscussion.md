# 6. Incremental TypeScript Adoption (Frontend) — Discussion

**Status:** `[discussion]` — no implementation yet. Decide direction before any conversion.
**Origin:** Spun out of the Playwright E2E setup (`claudePlans/5.PlaywrightTesting.md`). The Playwright tests are written in TypeScript; that prompted the question of whether the whole frontend should adopt TS.

## The question

Playwright itself is written entirely in TypeScript. Should `npmfrontend/` follow suit?

## Why Playwright is TypeScript (and why that logic only partly transfers)

Playwright's reasons are mostly **library** reasons, not app reasons:

1. **For a library, the types *are* the product.** Playwright ships `.d.ts` files so millions of downstream users get autocomplete and compile-time checking of its API for free. That payoff only exists if you publish an interface. This app has no external consumers — just its author.
2. **Large team, high contributor churn, huge API surface.** TS's refactoring safety and self-documentation scale with team size and surface area. Playwright is a big Microsoft project; this is a solo project.
3. **It's a Microsoft project.** Microsoft created TypeScript; it's the house language. Culture, not a universal law.

So "the creators know something I don't" is true, but what they know is *"types are extremely worth it for a widely-consumed, team-maintained library."* Different equation than a solo app.

## Pros of converting the frontend

- **Catches exactly the bugs that keep biting this project.** The recurring `eventMapper` PascalCase↔camelCase confusion, lat/long ↔ `Latitude/Longitude`, Redux action-payload shape drift — all compile-time catches. (Concrete example: the Playwright fixture bug found during setup, where a camelCase fixture silently produced empty events, is a textbook TS catch.)
- **The backend is already strongly typed (C#).** A typed frontend can mirror the backend `Event` DTO once and have the compiler flag mapper drift — precisely the seam where the bugs live.
- **Refactor confidence + IntelliSense** across the Three.js / R3F / Redux APIs (all ship good types).

## Cons / costs

- **Real migration effort** on an existing React/Redux/Three.js codebase. Incremental, but ongoing work competing with feature TODOs.
- **Already 292 lint problems** (see the "Review and clean up lint errors" Code Quality TODO). TS will *initially surface more* issues, not fewer — front-loaded pain.
- **R3F JSX typing is fiddly.** The existing `react/no-unknown-property` lint friction is a preview of typed-Three.js-in-JSX papercuts.
- **Solo-dev discount.** TS's team-coordination wins are muted for one person (not zero — "future me in six months" counts).
- **Occasional friction for dynamic/experimental code** — shaders and prototyping new globe interactions are where types help least.

## Recommended path (if pursued): type the data-model boundary first

Don't big-bang convert. Vite supports `.ts`/`.tsx` alongside `.js`/`.jsx` with `allowJs: true`, so convert file-by-file, highest-value first:

1. Start where bugs cluster: `src/api/eventMapper.js`, `src/api/historyEventApi.js`, and the Redux slice payloads. Define the backend `Event` shape once (mirror the C# model).
2. Lighter alternative to renaming: keep `.js` files but add **JSDoc type annotations + `checkJs`** in a tsconfig. ~70% of the checking, zero renames, fully reversible — a good way to trial TS before committing.

## Important cross-dependency (the reason this is `[discussion]`, not `[simple]`)

Several pending architectural TODOs would **reshape the very data-model types** TS would encode. Typing the data model now, then reshaping it, means re-typing churn. Sequence TS adoption *after* these land:

- **"Sources as a distinct object vs. events tagged 'creation of source'"** (Design Discussions) — would collapse `EventSource` into `Event`, rewriting the source-related types entirely.
- **"Date storage in days relative to 0 AD with Julian calendar conversion"** (Design Discussions) — would replace the flattened `LBYear/Month/Day…` fields with a different representation.
- **"Wire image upload to backend"** + **`eventIsCreationOfSource` backend field** (Refactors) — adds/changes fields on the `Event` model and mappers.
- **"Frontend state persistence strategy"** (Design Discussions) — may restructure the Redux slices whose payloads TS would type.

## Decision needed

- Adopt TS incrementally now (data-model boundary first), or defer until the data-model-reshaping discussions above resolve?
- If adopting: full `.ts` conversion of the boundary files, or the lighter JSDoc + `checkJs` trial first?
