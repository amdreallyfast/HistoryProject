# 4. Region / Pin Drag Performance Fix

**Branch:** `bugfix/region-drag-perf` (off `test`)
**TODO source:** "Bug: Repeated region/pin moves cause React error #185 and THREE.js context loss."

## Problem

After moving the editable region or boundary pins many times during edit mode, the
console reports:

- `Minified React error #185` ("Maximum update depth exceeded")
- `THREE.js context lost`

The bug is reproducible by entering edit mode on an event and dragging the region
polygon back and forth for several seconds.

## Root cause

Every native DOM `mousemove` (≈120Hz) drives a deep cascade through React + Redux:

1. `GlobeSectionMain.onCanvasMouseMove` → `setMousePos(...)` — one Redux dispatch
   per `mousemove`.
2. `MouseHandler.useEffect[mouseState.currPos]` runs on each `setMousePos` and,
   while click-and-drag is enabled, dispatches `updateClickAndDrag(rotorData)`
   — a fresh `clickAndDrag` object with a fresh `rotorQuaternion` every time.
3. Every `EditPinMesh.useEffect[editState.clickAndDrag?.rotorQuaternion]` fires
   for every pin. In the region-mesh drag case (`moveAllPins`), all 9 pins
   (1 primary + 8 region) each dispatch — **9 sequential Redux dispatches per
   mousemove**:
   - 1× `setPrimaryLoc(loc)` → new `primaryLoc` reference
   - 8× `updateRegionBoundary(loc)` → new `regionBoundaries` reference each
4. `EditRegionMesh.useEffect[editState.regionBoundaries]` runs the ear-clipping
   algorithm (`generateRegionMesh`) and allocates fresh
   `THREE.Float32BufferAttribute` + `Uint32BufferAttribute` to assign to the
   mesh. Drei `<Line>` receives a fresh points array and rebuilds its geometry.
5. `setLinePoints(linePoints)` inside that same useEffect triggers another
   EditRegionMesh re-render.

Even when React 18's auto-batching collapses the 9 dispatches in step 3 into one
re-render, the per-mousemove cost is still:

- one ear-clipping pass,
- two new GPU buffers + one Drei line geometry rebuild,
- a Float32Array re-allocation.

At 120Hz that is ~120 GPU buffer allocations per second of dragging. After
enough frames the WebGL driver runs out of headroom and reports
`context lost`. React's "max update depth" guard fires when the queue of
cascading state updates is deep enough that React can't drain it inside its
safety budget.

The pin meshes themselves are already mutated in-place via refs
(`EditPinMesh.jsx:165-176`). The position bookkeeping that flows through Redux
during the drag is not actually needed until drag ends — it just exists to keep
the polygon mesh visually in sync.

## Implementation plan

Three steps, one commit each, with testing between. Start with Steps 1 + 2;
only do Step 3 if the polygon snap-on-release feel is unacceptable.

### Step 1 — Cap drag dispatches at 1/frame

Move the body of `MouseHandler.useEffect[mouseState.currPos]` into a `useFrame`
hook. `useFrame` runs once per requestAnimationFrame (~60Hz), so multiple
browser `mousemove` events between frames coalesce into a single
`updateClickAndDrag` dispatch.

The `useEffect[currPos]` is removed. The state-transition logic (the
`enableClickAndDrag` branch) moves into the same `useFrame` since it's gated by
the same guards.

**Why this matters:** Drops `rotorQuaternion` update rate from ~120Hz to ~60Hz
and prevents React from falling behind the event queue. This alone may resolve
React error #185.

**File:** `npmfrontend/src/GlobeSection/MouseHandler.jsx`

### Step 2 — Stop dispatching boundary state during drag; commit on mouseUp

Each `EditPinMesh.useEffect[rotorQuaternion]` already mutates its mesh + box in
place. The dispatches at the end (`setPrimaryLoc` / `updateRegionBoundary`) are
the perf bomb because they drive the per-frame `regionBoundaries` reference
churn that triggers the ear-clipping + buffer reallocations downstream.

Changes:

- `EditPinMesh.useEffect[rotorQuaternion]`: keep the in-place mesh/box mutation.
  Remove the trailing `setPrimaryLoc` / `updateRegionBoundary` dispatches.
- `EditPinMesh.useEffect[leftMouseUp]`: extend so each pin dispatches the
  appropriate update (`setPrimaryLoc` for primary, `updateRegionBoundary` for
  region) using its current mesh position. This runs once per drag, not 120
  times per second.
- No reducer changes needed — same actions, called less often.

**Trade-off:** During an active drag, the polygon mesh between the pins stays
stale (no boundary state updates → no regeneration). The pins themselves still
move live. On mouseUp the polygon snaps to its new shape. This is the gap
Step 3 closes.

**Files:**
- `npmfrontend/src/GlobeSection/EditPinMesh.jsx`

### Step 3 — Keep the polygon mesh live without going through Redux *(deferred until Steps 1 + 2 tested)*

If the snap-on-release behavior from Step 2 feels bad, restore live tracking
without re-introducing per-frame Redux dispatches:

- `EditRegionMesh` gets a `useFrame` that runs only when
  `editState.clickAndDrag` is active. It reads pin world positions directly
  from the scene-graph group (or via a shared refs map).
- Update the existing `Float32BufferAttribute.array` in place — `needsUpdate =
  true`. **No new attribute allocations, no ear-clipping re-run** during drag
  (topology is preserved for translation; minor single-pin drags on convex
  polygons keep the existing triangulation valid).
- The current `useEffect[regionBoundaries]` is kept for post-mouseUp
  regeneration and for length changes (future Subdivide button).

**File:** `npmfrontend/src/GlobeSection/Region/EditRegionMesh.jsx`

## Files to modify

- `npmfrontend/src/GlobeSection/MouseHandler.jsx` (Step 1)
- `npmfrontend/src/GlobeSection/EditPinMesh.jsx` (Step 2)
- `npmfrontend/src/GlobeSection/Region/EditRegionMesh.jsx` (Step 3, deferred)

## Acceptance criteria

After Steps 1 + 2 ship:

- Drag the editable region polygon continuously for 30+ seconds — no React
  error #185, no THREE.js context lost.
- Drag individual boundary pins — same.
- On mouseUp, the polygon snaps to the new shape (or follows live if Step 3
  ships).
- Submitting after a drag persists the new pin positions to the backend
  identically to before.
