# 8. Share unchanged images across revisions, and slim the image-heavy requests

Branch: `perf/image-sharing` (from `test`). One PR into `test`; one commit per step.
Status: **approved 2026-11-25 (all of A–F); image upload cap stays 5 MB for now.**

## Baseline (local Docker SQL, before any change)

Measurement script (not committed): one event with a 4.5 MB JPEG-signature image, 2 tags, a 4-point region, 1 source with 2 authors; 5 text-only edits, each re-sending the image as today's frontend does.

| Request | Time | Transfer |
|---|---|---|
| `Create` (each) | 0.6–1.9 s | 6.0 MB up, 6.0 MB down |
| `GetAllRevisions` after rev 1 / 2 / 3 / 4 / 5 | 2.9 / 4.0 / 5.7 / 7.4 / **9.4 s** | 6 / 12 / 18 / 24 / **30 MB** |
| `GetFirst100` | 2.1 s | 6.0 MB |
| Stored for this one event | **5 image rows, 22.5 MB, 5 different hashes** of identical bytes | |

Local SQL is far faster than Azure Basic (where the same pattern took 15–45 s), but the growth with each revision is the same.

## Why

A HAR capture from the test site (2026-11-25) of one edit to an event with a ~4.5 MB image:

| Request | Server wait | Total | Size |
|---|---|---|---|
| `GetFirst100` (search) | 26 s | 31 s | 6.7 MB down |
| `POST Create` (submit) | 15 s | 21 s | 6.0 MB up + 6.0 MB down |
| `GetAllRevisions` ×5 after submit | 15–45 s each | 18–51 s each | 5.9 → 11.7 MB each |

Causes, all confirmed in code:
1. **Every revision stores its own copy of the image.** `eventMapper.frontendToBackend` sends the full bytes with a fresh random `EventImage.Id` on every submit, and `Create` inserts a new `Images` row. History size grows by the full image on every edit.
2. **The image fingerprint is random.** `EventImage.ImageBinary`'s setter computes `ImageMD5Hash` with `new HMACMD5()`, which generates a **random secret key per instance**, so identical images get different hashes. The stored hashes can't detect duplicates today.
3. **Reads multiply the image inside SQL.** Every read uses one query with several collection `Include`s (Tags, Region, Sources→Authors). EF's single-query mode returns one row per combination, repeating the event's columns, including the joined `ImageBinary`, in each row. EF already logs a warning about this (`MultipleCollectionIncludeWarning`). On the Basic SQL tier this is the most likely cause of the 15–45 s server times.
4. **The submit response echoes the image back** (6 MB), though the frontend ignores it: `EditEvent` re-fetches `GetAllRevisions` and treats that as truth.
5. **Revision history refetches on every window focus.** `RevisionStack` uses React Query defaults (`refetchOnWindowFocus: true`, `staleTime: 0`), producing the 4 extra 35–51 s requests after the submit.

Good news: the schema already supports sharing. `Event → EventImage` is many-to-one (`HasOne(EventImage).WithMany()`), so many revisions can point at one image row with **no table change**.

## Design changes (need your OK)

| # | Change | Impact |
|---|---|---|
| A | **Share images within an event's revision chain.** On submit, if the image is unchanged, the new revision points at the existing image row instead of storing a copy. | Storage and payload per edit drop to roughly the text that changed. Revision history size stops growing with the image. |
| B | **Unchanged images aren't re-uploaded.** The frontend remembers the backend image `Id`; if the image wasn't changed in the editor, it sends a reference instead of the bytes. API contract: new optional `ExistingImageId` on the Create payload. The server reuses it **only** if it belongs to an earlier revision of the **same** `EventId` (a client can't attach another event's image); otherwise 422. If the bytes *are* sent but match an earlier revision's image by hash, the server still reuses (covers re-uploading the same file). | Submit upload drops from 6 MB to a few KB when only text changed. |
| C | **Deterministic fingerprint.** Replace `HMACMD5` with plain `MD5.HashData` (same 32-hex-char column, no schema change), plus a migration that recomputes existing rows' hashes in SQL (`HASHBYTES('MD5', ImageBinary)`). MD5 is fine here: it's a duplicate detector, not a security control, and reuse is scoped to one event's own images. | Fixes the hash; required for the "same bytes" path in B. |
| D | **Split queries** for every multi-`Include` read (`.AsSplitQuery()`). | Each collection loads in its own query; the image is read once per event instead of once per row combination. Most likely the biggest server-time win. |
| E | **Slim `Create` response**: return `{ Id, EventId, Revision, RevisionDateTime }` instead of the whole event with image. | Removes the 6 MB echo. Frontend doesn't use the body today. |
| F | **Revision history: no refetch on window focus** (`refetchOnWindowFocus: false`; revisions are immutable, and a new revision already triggers a refetch after submit). | Removes the repeated 35–51 s reloads. |

**Scoped out, on purpose:**
- **Sharing identical images across *different* events.** Deleting an image row cascades to every event that references it (`OnDelete(Cascade)`), and `Delete` removes each revision's image. Within one event that's safe (Delete removes the whole chain). Across events it would need reference-counting in `Delete`. Possible later; not needed for the problem at hand.
- **Lazy-loading images out of `GetFirst100`** (existing `[plan first]` TODO). After A–F, search still carries each event's latest image once. That item is the next step after this one.
- **Shrinking images before upload.** Separate UX decision (see question 2).

## Open questions

1. **Scope:** do all of A–F in this PR (recommended: they're each small, and together they fix the slow edit you saw), or just A–C (sharing) first?
2. **Image size limit:** keep the 5 MB upload cap as is for now (recommended), or open a separate TODO to resize large photos in the browser before upload (e.g. longest side 1920 px)? That changes what gets stored, so it's your call.

## Steps

0. **Baseline measurement.** Local Docker SQL: seed an event with a ~4.5 MB image and 5 revisions; time `Create`, `GetAllRevisions`, and `GetFirst100`, and record bytes transferred. Local SQL is much faster than Azure Basic, so compare relative numbers.
1. **C: deterministic hash** + backfill migration. Unit test: same bytes → same hash; different bytes → different hash.
2. **D: split queries.** Re-measure.
3. **A + B: image sharing.** Backend: `ExistingImageId` handling, hash-match reuse, same-chain check, `Delete` still removes the chain's images exactly once. Frontend: carry the image `Id` through `backendToFrontend` → edit state → `frontendToBackend`; send `ExistingImageId` when `imageDataUrl` is unchanged. Tests: backend unit tests (reuse by id, reuse by hash, new image inserts, foreign-chain id rejected, delete with shared image); Vitest mapper test; Playwright: editing only the title posts no image bytes.
4. **E: slim `Create` response.** Update the existing tests that read the response.
5. **F: revision history refetch.** Playwright: switching focus away and back doesn't refetch.
6. **Measure again**, record before/after in this doc; DESIGN.md (revision storage model, image sharing rule); TODO updates.

## How you'll check it

On the test site after merge (first request may still be slow while it wakes): open your image-heavy event, change only the title, submit. The submit should take seconds, not ~20 s, and the revision history should stop growing by the image size. Changing the image itself should still work and show the new image.
