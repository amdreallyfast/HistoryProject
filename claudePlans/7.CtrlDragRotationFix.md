# 7. Camera moves while dragging a pin or region (Ctrl+drag bug)

TODO item: Bug Fixes → **Globe: Ctrl+drag on a pin still rotates the globe when the canvas didn't have focus first.** (`[plan first]`)
Branch: `fix/ctrl-drag-rotation` (from `test`). One PR into `test`.

## Revision (2026-11-25)

The first draft fixed the Ctrl key (window-level tracking + a "Hold CTRL" banner). The user asked instead: **disable camera rotation automatically while dragging a pin or the region**, which is what Ctrl existed for, provided it doesn't tangle the components together. An experiment showed this is feasible and clean; this plan replaces the Ctrl approach.

## Root cause (confirmed in code)

- three.js `OrbitControls` decides what a drag does in its own `pointerdown` handler (`OrbitControls.js` ~line 1677). Nothing stopped it when the press landed on a pin or the region, so the camera and the pin both moved. Ctrl was the manual workaround; it only reached the canvas when the canvas had keyboard focus.

## The approach: `CameraDragLock` (prototyped, tests passing)

A small, self-contained component inside the `<Canvas>`:
- **When:** a left-button press, in edit mode, whose first raycast hit is an editable pin (`PinBoundingBox`) or the editable region (`Region`).
- **Does:** sets `controls.enabled = false` on the camera controls, synchronously, from a capture-phase `pointerdown` listener on `window` (runs before OrbitControls' own handler).
- **Releases:** on `pointerup` anywhere, `pointercancel`, or window `blur`, so the camera can't stay frozen.

**Why the components stay independent:**
- It decides "what was grabbed" from the **same** per-frame raycast (`mouseInfoReducer.cursorRaycasting.intersections[0]`) that `GlobeSectionMain`/`MouseHandler` already use to start a drag, so the lock and the drag can't disagree.
- Pins, region, and `MouseHandler` are untouched. The only other change is `makeDefault` on `<OrbitControls>`, so the lock can find the controls.
- It only touches `controls.enabled`, which nothing else uses; the Ctrl toggle uses `enableRotate`/`enablePan`.

**Test support:** `GlobeTestHook` exposes `window.__globeTest` (camera position, a pin's on-screen position by location id, any lat/long's on-screen position) in **non-production builds only**; verified absent from the production bundle.

## Experiment results

New `tests/globe-drag-camera-lock.spec.ts` (5 tests, passed 3× in a row):
1. Dragging a pin, with focus first on the Title box: pin moves, camera doesn't.
2. Dragging the region: all boundary points move, camera doesn't.
3. Edit mode, dragging empty globe: camera rotates (twice, so the lock is released).
4. After a pin drag, dragging empty globe rotates again.
5. Display mode, dragging over an event's region: camera rotates (lock is edit-mode only).

With the lock commented out, tests 1 and 2 fail (camera moves), reproducing the bug; 3–5 still pass. Full suite: lint clean, 119 Vitest, 41 Playwright, build OK.

Finding during the experiment: the shared fixture's primary pin sits almost on a boundary pin, so a press can grab the primary instead. The new spec uses its own larger region with separated pins.

## Press-time raycast (added 2026-11-25, approved)

**Timing measured** with temporary probes over 120 presses: the per-frame hover raycast trails the cursor by 1–2 frames (pressing 0–8 ms after arriving used the previous position's result every time; 16 ms ⅓ of the time; ≥33 ms never). The lock and `MouseHandler` always agreed (both read the same stored value), so the lock inherited the existing lag but never contradicted the drag. Release: the lock re-enables the camera on `pointerup`, about one frame (~20 ms) before `MouseHandler` ends the drag in its `useEffect`; harmless, since the controls only start moving on a new press.

**Change:** `cursorRaycast.js` holds the single "what's under this point?" function. `Scene` registers it (it owns the camera, the shared R3F raycaster, and the cached mesh list) and uses it for the per-frame hover as well. `GlobeSectionMain.onCanvasMouseDown` and `CameraDragLock` each call it at the pressed pixel (two independent calls per press in edit mode, one in display mode; same inputs, so same answer). Pixel conversion for both hover and press now uses the canvas's on-screen rectangle instead of hand-computed container offsets.

**Tests added:** pressing the instant the cursor reaches the region drags the region; pressing the instant it leaves rotates the camera; clicking an event on the globe selects it and clicking empty globe deselects. With the old stored-result behavior forced, the two fast-press tests fail.

**Commits so far:** step 1 (lock + test hook + spec), step 2 (press-time raycast).

## Remaining decision: what happens to Ctrl?

With the lock, Ctrl's original job is done automatically.
- **Option A (recommended): remove the Ctrl toggle.** Delete the canvas `onKeyDown`/`onKeyUp` handlers and the `cameraRotateEnabled`/`cameraPanEnabled` state. Simpler, nothing to learn, no focus bug left. Note: OrbitControls' built-in behavior remains, where Ctrl/Shift + left-drag on empty globe **pans** instead of rotating.
- **Option B: keep Ctrl** as-is for freezing the camera at other times (it still has the focus bug).

The "Hold CTRL: Stop rotation" banner is dropped either way.
