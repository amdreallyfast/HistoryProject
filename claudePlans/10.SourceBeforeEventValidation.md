# 10. Reject a source dated entirely before its event

TODO item: **A source dated entirely before its event is accepted** (Bug Fixes).

## The rule (confirmed with the user 2026-11-25)

For each source on an event, comparing the event's time range to the source's publication range:

| Case | Result |
|---|---|
| Source's latest date is before the event's earliest date (source entirely before event) | **Error**: Submit blocked; `Create` returns 422 |
| Ranges overlap | Allowed (the future "uncertain" flag, out of scope here) |
| Event ends before the source begins | Allowed, normal |

So the check is: **event earliest ≤ source latest**, for every source. Equal is allowed (written the same day).

## Current state

- **Frontend** `detailRestrictions.isDateRangeInverted` compares year → month → day, and gives up ("not inverted") when one side lacks a month or day. `EditEvent.hasDateErrors` uses it to block Submit; `EditEventTime` and `EditSourcePublicationTimeRange` show their own messages (`rangeError`).
- **Backend** `EventValidation.OrderError` compares **years only**, so it accepts e.g. "earliest 2026-10, latest 2026-03" that the frontend rejects.
- Years are plain integers, negative = BC (`convertTimeRangeToString`). Month and day are optional; year is required.
- Validation runs on `Create` only, so existing stored revisions are never re-checked.

## ⚠ Design decision (needs your OK): comparing partial dates

A bound with a missing month or day is a span, not a point. To compare two bounds, expand each to the widest point it could be:
- an **earliest** bound with missing parts → the **start** of that period (month → 1, day → 1)
- a **latest** bound with missing parts → the **end** of that period (month → 12, day → 31)

Then compare as (year, month, day). This is lenient: it only reports an error when *every* reading of the dates is impossible. Example: event earliest "1066", source latest "1066-03" → 1066-01-01 ≤ 1066-03-31, so it's allowed.

Day 31 for every month is deliberately simple. Real month lengths and leap years belong to the `JulianCalendar` item, which can later swap in exact month ends without changing callers.

Impact: none on stored data and no migration. One behavior change: the same comparison replaces the backend's years-only order check (event range and each source range), so the backend now rejects within-year inverted ranges, matching what the frontend already blocks.

## Steps

1. **Shared comparison, with shared test cases.**
   - Frontend: `src/dates/partialDate.js` exports `earliestKey(y, m, d)`, `latestKey(y, m, d)` (comparable numbers) and `isSourceBeforeEvent(eventTime, publicationTime)`. Missing or non-numeric years → no verdict (other checks already report those).
   - Backend: `Validation/PartialDate.cs` with the same functions.
   - One JSON file of cases (`npmfrontend/src/dates/partialDateCases.json`: BC years, missing month/day on either side, equal bounds, same year) read by **both** Vitest and an MSTest test, so the two implementations can't drift. This follows the existing cross-tier contract-test pattern.
2. **Backend.** `ValidateSourceDates` adds: if `PartialDate.IsSourceBeforeEvent(...)` → 422 naming the source, e.g. *"Source 'X' (latest 1050) can't be dated before the event's earliest date (1066)."* `OrderError` uses the same comparison. Unit tests: 422 for a source entirely before the event; OK for overlap, equal dates, and a source after the event.
3. **Frontend.**
   - `EditEvent.hasDateErrors` also returns true if any source is before the event, so Submit is blocked.
   - `EditSourcePublicationTimeRange` shows the message under that source's dates (red, like its other range errors). It's computed from Redux on each render, from the event's time and that source's dates, so it updates when *either* is edited.
   - `isDateRangeInverted` is reimplemented on the shared keys, with identical results (verified by its existing tests).
4. **Playwright.** New event with a source: source latest before event earliest → message shown, Submit disabled. Then move the event earlier → message gone, Submit enabled. Also an overlap case (no error).
5. **Docs.** DESIGN.md: the rule, the partial-date expansion, the note that overlap will raise the uncertainty flag later. TODO.md: mark the item done once you've tested.
6. **PR into `test`**, merge when green. You try on the test site: a source before the event is blocked; overlap and "event before source" both submit.

## Not in scope

- The uncertainty flag for overlaps (its own `[discussion]` item).
- Re-checking already stored revisions. One that breaks the rule can still be read; editing it will show the error until the dates are fixed.
- Selecting an existing source instead of creating one doesn't exist yet. When it does, it goes through the same `EditSource` state, so the check applies automatically.
